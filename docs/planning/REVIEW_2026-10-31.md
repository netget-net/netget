# Review — 31 October 2026

A hands-on pass over the installed `netget --mcp` (HTTP, Redis, PostgreSQL and Telnet servers,
a Redis client, manual intercepts, error paths) plus a check of the planning backlog against
source. Items are grouped into workstreams (W1…W20); each workstream is one agent on its own
branch, merged into `master` with `--no-ff`.

Legend: `[ ]` open · `[~]` in progress · `[x]` done (merged) · `[?]` needs a decision from the
maintainer · **(repro)** reproduced by hand on 31 Oct · **(backlog)** from the planning docs,
verified against source.

## A. Bugs reproduced by hand

### W1 — MCP and handler correctness
- [ ] **2. `*` static handlers are validated against every protocol's actions.** A redis server
  started with `send_http_response` as its catch-all; every command then answered
  `ERR no response produced`. The rejection message for an unknown action lists ~2 000 actions
  from every protocol (`src/events/handler.rs:3015-3050`). Scope both to the server's protocol.
  **(repro)**
- [ ] **5. Parked intercepts outlive their connection.** Answering one whose peer had gone
  reported "Answered" and counted 31 bytes written to a closed connection. Reap on close; refuse
  the answer. **(repro)**
- [ ] **9. `__UPDATE_UI__` leaks into MCP tool output** (`start_server` result;
  sent from `src/server/peer_support.rs:173`). **(repro)**
- [ ] **15. Intercepts offer the protocol's whole action set** instead of the event's own
  (redis SUBSCRIBE offered ~18 where its docs list 4). **(repro)**
- [ ] **11a.** A server started with only `event_handlers` still gets the substituted
  "You are a redis server. Handle requests appropriately." instruction. **(repro)**
- [ ] **11b.** Unknown startup-param error says "Protocol must declare this parameter in
  get_startup_parameters()" — developer wording on a user-facing surface. **(repro)**
- [ ] **11c.** Disconnected clients stay in `list_clients`. **(repro)**
- [ ] **11d.** Server ids jump (#1 → #7); confirm it is the shared id counter and say so, or fix. **(repro)**

### W2 — Model selection and settings
- [ ] **1. A configured model that is not installed is reported as current**, and every request
  fails in ~40 ms with "LLM failed to generate valid response after retries" — no retry
  happened. Validate at startup and in `get_status`, name "model not installed", fall back to an
  installed model. **(repro)**
- [ ] **10. Saved scripting mode `on` is rejected by the settings parser** (`src/settings.rs:134`
  knows llm/python/javascript/go; the CLI also accepts on/off/perl). Warned and ignored on every
  start. **(repro)**

### W3 — LLM behaviour (core prompt and actions)
- [ ] **3. `show_message` is taken for a wire reply.** The Telnet BBS greeting and first reply
  went to the operator log; the peer saw nothing. Rename (keep the old name as an alias) and keep
  it off events that expect a reply. **(repro)**
- [ ] **4. Memory is server-wide.** `user_name: Zed` (appended twice) would greet the next peer as
  Zed. Per-connection memory or keyed memory that overwrites. **(repro)**
- [ ] **6. Clients repeat their opening instruction.** "PING, then GET mykey, then stop" sent
  PING+GET seven times before disconnecting. **(repro)**
- [ ] **13. Prompt example teaches a needless `generate_random uuid` call**
  (`prompts/shared/partials/response_format.hbs:83`). **(backlog)**

### W4 — Protocol wire fixes
- [ ] **7. Redis server flattens argv**: `SET k "a b c"` arrives as `"SET k a b c"`
  (`src/server/redis/mod.rs:1352`). Add an `args` array. **(repro)**
- [ ] **8. HTTP answers a silent model with a blank `200`** — a known, labelled fail-open
  (`src/server/http/mod.rs:701`). Answer 5xx when no `default_response` is configured; check
  the other `http_common` users. **(repro)**
