# Review — 13 November 2026

The open items of `REVIEW_2026-11-08.md`, taken one workstream each. Every row says what was
found by doing it, not only what was built; each fix has a test that fails without it.

Legend: `[ ]` open · `[x]` done (merged).

## S1 — Dashboard TUI scrolling  [x]

- [x] The routing table and the intercept modal scroll through the same `draw_scrolled` as the
  form, composer and routing draft (`View::Selection` follows the cursor, `View::From` a scroll
  offset); a read-only modal that does not fit says there is more.
- [x] ↑/↓ scroll the answer modal's request; Tab and ←/→ move between its buttons.
- [x] The picker listed servers and clients in an order the arrow keys did not follow.

## S2 — Headless use: MCP and CLI  [x]

- [x] A wrong MCP argument names its field and the expected type
  (`src/mcp_stdio/params.rs`, `serde_path_to_error`), instead of rmcp's bare "invalid params".
- [x] `-h` is one line per flag (5.3 KB, from 12 KB); `--help` keeps the detail and the
  examples. The deprecated `--ollama-lock` is documented in `--help` only.
- [x] `--server` and `--client` resolve a protocol name exactly as MCP does (`resolve_name`):
  an alias two protocols share is refused with both names.
- [x] The scripting runtimes (Python, Node, …) are probed when a script handler first needs
  one, not at every start (`AppState::scripting_mode_available`).
- [x] `answer_intercept`'s error lists only the actions the parked event accepts.

## S3 — FTP's remaining verbs  [x]

- [x] Binary files: `send_ftp_data` takes `encoding: "utf8"|"hex"`, a binary upload reaches
  the handler as `upload_hex` (bounded by `max_hex_upload_bytes`, 64 KiB).
- [x] `REST` restarts `RETR` and `STOR` in stream mode (`554` past the end); `STOU` names its
  file in `150 FILE: <name>`.
- [x] `ABOR` during a transfer. The control reader is cancel-safe (`src/server/ftp/control.rs`)
  and the control socket is `SO_OOBINLINE`, because python's `ftplib.abort()` sends the `\n`
  of `ABOR\r\n` as TCP urgent data.
- [x] Explicit FTPS (`AUTH TLS`, `PBSZ`, `PROT P`, `src/server/ftp/tls.rs`), verified by
  ftplib's `FTP_TLS` and curl `--ssl-reqd`; `require_tls` refuses `USER` before `AUTH TLS`
  (530) and a data channel without `PROT P` (521), and every event carries `tls`.
- [ ] Open: implicit FTPS on port 990, `CCC`.

## S4 — DNS padding  [x]

- [x] DNS, DoT, DoH and DoQ pad a reply to a multiple of 468 octets (RFC 8467) when, and only
  when, the query carried an EDNS(0) Padding option (`Reply::pad`); SERVFAIL keeps its OPT.
  `tests/server/<p>/padding_test.rs` per transport.
- [x] The DoT client displayed records through a formatter that could panic on an unusual
  RDATA; it uses `try_display`.

## S5 — Model behaviour  [x]

- [x] Prometheus histograms: the model gives per-bucket counts (`bucket_counts`) and NetGet
  makes them cumulative — the arithmetic llama3.1:8b got wrong.
- [x] Bolt's "accepts any login": `EventType::decision_only` offers a yes/no event its two
  answers and nothing else; 14 of 120 wrong refusals became 0 of 120
  (`eval-results/2026-11-13-structural-cases/`). Baseline regenerated: 496/525.
- [ ] Open: other protocols' login events could be `decision_only`; Docker cases were not
  re-run where `docker` exists.

## S6 — Stable: etcd and postgresql  [x]

- [x] Both Stable on the six conditions. The "second client" of each shared the server's codec
  (etcd-client is tonic/prost, tokio-postgres decodes with `postgres-types`); Python grpcio and
  psycopg 3 over libpq are the second clients now.
- [x] etcd: a Txn was decided on the counts of its compares, its reply carried no results,
  Range's `limit`/`keys_only`/`count_only` were ignored; a 48 MiB server-wide body budget
  replaces a per-request bound that bounded nothing in total, and an idle bound now fires on a
  request whose body stopped arriving.
- [x] postgresql: the model never saw a bound parameter; a binary `date` went out as text and
  an oversize cell as `0`. Unauthenticated messages are capped at 1 MiB by
  `src/server/postgresql/guard.rs` (pgwire allowed 1 GB).
- [ ] Open: CI's grpcio and psycopg installs have not run on a hosted runner; the pgwire
  fork could take a configurable size limit upstream.

## S7 — Stable: websocket, mqtt, kafka  [x]

- [x] `websocket` is Stable. Python websockets and Node ws drive every verb (websocat a subset)
  through the pcap oracle. The inbound queue had no bound (a peer outrunning its handler was
  read into memory without limit; now 1024 messages or 8 MiB); a compressed frame was not
  held to `max_frame_size`; a frame tungstenite refused dropped the socket with no close frame
  (now 1009 / 1002 / 1007); an over-long request head got no answer (now 431 at 16 384 bytes).
- [x] The backpressure bound's first tests never reached the frame loop: their `*` → manual
  rule parked `websocket_connection_opened`, which is answered before anything is read. The
  dashboard's own default had the same effect on every connection; the opened event is now
  `raised_on_every_connection()`, so the dashboard answers it with nothing
  (`tests/server/websocket/dashboard_routing_test.rs`).
- [x] `mqtt` is Stable. The broker ignored a client's PUBREC, so a QoS 2 subscriber never
  received a QoS 2 message; a second CONNECT with a live client id did not take it over and
  the first's teardown removed the second's entry; `max_packet_size` counted the remaining
  length; the codec now refuses what the specification says a broker MUST.
- [x] `kafka` stays Beta. A Produce v0–2 request of nested compressed legacy wrappers (34 bytes
  a level) overflowed the stack and killed the process; compressed legacy sets are now
  answered `UNSUPPORTED_COMPRESSION_TYPE` before the decoder sees them
  (`legacy_nesting_test`). `request_bounds_test` holds the per-request bounds on both sides,
  and both AGENTS.md files were re-verified (~15 false claims fixed).
- [ ] Open (kafka): no third-party client sends OffsetCommit (condition 1); the 30 s / 600 s
  deadlines and the connection cap have only a source ratchet; most of kafka's bound tests run
  in no CI job.
- [ ] Open (upstream, not filed): `kafka-protocol` keys an unknown tagged field with a tag
  ≥ 2^31 as a negative `i32`, which `encode` counts but never writes, so encode → decode fails
  (repro: ApiVersionsRequest v3 body `01 01 01 ff ff ff ff 0f 01 78`); an over-long
  `UnsignedVarInt` is truncated at 5 bytes rather than refused. The broker never re-encodes a
  request, so NetGet is unaffected; the `kafka_request` fuzz target exempts that shape.

## Final verification

On the combined master: `cargo fmt --check`; clippy over all targets with
`-D clippy::correctness -D clippy::suspicious` (clean); `scripts/test_batches.sh` (267 targets,
2 196 passed, 1 failed); CI's protocol suites plus every suite this round touched (532 passed,
5 failed). What failed, and what came of it:

- `parameter_type_agreement_test`: etcd's put event declared the request's `prev_kv` flag as a
  boolean beside an answer whose `prev_kv` is the pair. The event field is `wants_prev_kv` now.
- `client::redis::cluster_redirect_bound_test` lost a probed port to another test between
  probing and binding; it retries the pair.
- Four real-peer tests (`doq` with dnsproxy, `kafka`'s Java and franz-go clients, `mqtt`'s
  paho v5) hard-failed on peers this machine had not installed, as they are written to.
  With the peers installed through each suite's own installer, `doq`, `kafka`, `mqtt` and
  `websocket` pass 141 of 141, and etcd's suite and the redis test pass on re-run.
