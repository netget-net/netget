# PyPI Protocol Implementation

## Overview

PyPI (Python Package Index) server implementing PEP 503 Simple Repository API. The LLM controls package availability,
version lists, and file serving while hyper handles the underlying HTTP protocol.

**Status**: Experimental
**RFC**: PEP 503 (Simple Repository API)

## Library Choices

- **hyper v1.0** - HTTP server library (same as HTTP protocol)
- **hyper-util** - Additional utilities for Tokio integration
- **http-body-util** - Body handling utilities
- **Manual PEP 503 compliance** - LLM generates HTML responses according to PEP 503 format

**Rationale**: PyPI is fundamentally an HTTP server with specific path conventions and HTML response formats. We reuse
the hyper infrastructure from the HTTP protocol implementation but add PyPI-specific logic:

- Path parsing to identify request types (list packages, list files, download)
- Request classification for the LLM
- PEP 503 HTML format guidance in event descriptions

The LLM focuses on application logic (which packages exist, which versions are available, what file contents to serve)
rather than HTTP or HTML formatting details.

## PEP 503 Simple Repository API

### Required Endpoints

1. **Root/Index endpoint** (`/simple/`):
    - Returns HTML5 page listing all available packages
    - Each package as an anchor tag: `<a href="package-name/">package-name</a>`

2. **Project endpoint** (`/simple/<package-name>/`):
    - Returns HTML5 page listing all distribution files for the package
    - Each file as an anchor tag with href and optional hash:
      `<a href="../../packages/path/file.whl#sha256=...">file.whl</a>`

3. **File download endpoint** (`/packages/<path>/<filename>`):
    - Returns the actual package file (wheel, sdist, etc.)
    - Content-Type should be appropriate for the file type

### URL Requirements (PEP 503)

- All HTML endpoints MUST end with `/`
- Project names should be normalized (lowercase, replace `_` and `-` with `-`)
- File URLs can be absolute or relative

### HTML Format

Both index and project pages must be valid HTML5 with anchor elements. Minimal example:

```html
<!DOCTYPE html>
<html>
<body>
<a href="package-name/">package-name</a>
</body>
</html>
```

## Architecture Decisions

### 1. HTTP-Based Implementation

PyPI is built on top of HTTP/1.1:

- Uses hyper for HTTP protocol handling (same as HTTP protocol)
- Each HTTP request is classified as `list_packages`, `list_files`, or `download_file`
- LLM generates appropriate responses based on request type

### 2. Request Classification

The server analyzes the request path to determine the type:

- `/`, `/simple` or `/simple/` → `list_packages`
- `/simple/<package>` or `/simple/<package>/` → `list_files` (package name
  extracted; PEP 503 project URLs end with `/`, but a client may omit it)
- `/packages/<path>/<filename>` → `download_file` (filename extracted into
  `package_name`)
- Other paths → `unknown`

This classification is provided to the LLM in the `request_type` parameter.

### 3. Connection Tracking

Similar to HTTP protocol:

- One `ConnectionId` per TCP connection (not per HTTP request)
- `ProtocolConnectionInfo::Pypi` tracks recent requests on the connection
- Multiple PyPI requests can occur on the same TCP connection (HTTP keep-alive)

### 4. Body Handling

Same as HTTP protocol:

- Request bodies buffered whole, but **bounded** by
  `http_common::handler::MAX_REQUEST_BODY_BYTES` (8 MiB) via `http_body_util::Limited`;
  a larger one is refused with **413** before any LLM call. `Incoming` has no default
  limit and this body is also interpolated into the LLM prompt, so an unbounded read
  allocated twice over at a size the peer chose — the unbounded-upload shape
- A read that fails is **not** replaced with an empty body: a truncated request handed
  to the model looks like a complete one and the model answers a request it never saw
- Response bodies generated by LLM as complete strings
- No streaming support

### 5. Dual Logging

All PyPI operations use dual logging:

- **DEBUG**: Request summary (method, URI, request type)
- **TRACE**: Full request details (headers)
- Both go to `netget.log` (via tracing) and TUI Status panel (via status_tx)

### 6. Error Handling

Every failure answers the peer, and answers it with a *category* only — the error
itself (backend URL, model name, anyhow chain) goes to the log and the status stream,
never to the socket. See `crate::utils::wire_failure`.

- **LLM/backend call failed** — `WireFailure::classify` decides the code:
  `Overloaded` → **503** with `Retry-After: 5` (pip backs off and retries),
  anything else → **500**. Body is the static category string.
  Logged as `decision=fail_closed_llm_error`.
- **The answer contained no `send_pypi_response`** (model said nothing, or a handler
  configured with `actions: []`) — **502**, logged as `decision=fail_closed_no_action`.
- **The answer cannot be put on the wire** (status outside 100-599, `body_base64` that
  does not decode, a header name hyper rejects) — **502**, logged as
  `decision=fail_closed_bad_action`.
- **The model answered** — its own status is sent as given, including a deliberate 404
  or 403. Logged as `decision=model_response`, so a model's refusal is distinguishable
  in the log from netget failing to get one.
- Hyper connection errors close the connection automatically.

There is deliberately **no permissive default**. This used to reply `200 OK` with an
empty body whenever nothing usable came back, which pip reads as "the project exists
and has zero distributions" — silence becoming a successful answer, the fail-open shape
CLAUDE.md calls the most dangerous pattern in the codebase.

## LLM Integration

### Action-Based Response Model

The LLM responds to PyPI events with actions:

**Events**:

- `pypi_request` - PyPI HTTP request received from client (pip, twine, etc.)
    - Parameters: `method`, `uri`, `path`, `headers`, `body`, `request_type`, `package_name`

**Available Actions**:

- `send_pypi_response` - Send PyPI HTTP response (status, headers, body)
- Common actions: `notify_operator`, `update_instruction`, etc.
- **No async actions** - PyPI is purely request-response

### Request Types

The LLM receives a `request_type` parameter indicating what kind of request this is:

1. **`list_packages`** - Client requests `/simple/`
    - LLM should return HTML listing all available packages
    - Each package as `<a href="package-name/">package-name</a>`

2. **`list_files`** - Client requests `/simple/<package-name>/`
    - `package_name` parameter contains the package name
    - LLM should return HTML listing all available files for that package
    - Each file as `<a href="../../packages/hash/filename#sha256=...">filename</a>`

3. **`download_file`** - Client requests `/packages/<path>/<filename>`
    - `package_name` parameter contains the requested file name, not a package name
    - LLM should return the actual file content
    - Text (PKG-INFO, setup.py) goes in `body`; real archive bytes go in
      `body_base64`

### Example LLM Response (list_packages)

```json
{
  "actions": [
    {
      "type": "send_pypi_response",
      "status": 200,
      "headers": {
        "Content-Type": "text/html"
      },
      "body": "<!DOCTYPE html>\n<html>\n<body>\n<a href=\"hello-world/\">hello-world</a>\n<a href=\"example-pkg/\">example-pkg</a>\n</body>\n</html>"
    },
    {
      "type": "notify_operator",
      "message": "Served package index"
    }
  ]
}
```

### Example LLM Response (list_files)

```json
{
  "actions": [
    {
      "type": "send_pypi_response",
      "status": 200,
      "headers": {
        "Content-Type": "text/html"
      },
      "body": "<!DOCTYPE html>\n<html>\n<body>\n<a href=\"../../packages/abc/hello_world-1.0.0-py3-none-any.whl#sha256=abc123\">hello_world-1.0.0-py3-none-any.whl</a>\n</body>\n</html>"
    }
  ]
}
```

### Example LLM Response (download_file)

A wheel is a ZIP archive. A model cannot write one; a script or static handler
that already holds the bytes sends them base64-encoded:

```json
{
  "actions": [
    {
      "type": "send_pypi_response",
      "status": 200,
      "headers": {
        "Content-Type": "application/octet-stream"
      },
      "body_base64": "UEsDBBQACAgIAAAAIQ..."
    }
  ]
}
```

pip verifies the download against the `#sha256=` fragment advertised on the
`list_files` page, so a handler serving `body_base64` must hash the same bytes.

### Response Format

The `send_pypi_response` action returns structured data:

```json
{
  "status": 200,
  "headers": {"Content-Type": "text/html"},
  "body": "<!DOCTYPE html>..."
}
```

A response using `body_base64` carries that field instead of `body`; the server
decodes it before writing the HTTP body.

### When No Valid Response Is Produced

There is no default response. If the answer carries no `send_pypi_response`, or carries
one that cannot be turned into an HTTP message, the request is answered **502** and the
reason is logged with a `decision=fail_closed_*` tag (see Error Handling above). The
connection and the server stay up. A status outside 100-599 is rejected by the action
executor and again by the transport path; a `body_base64` that does not decode is a 502
rather than a 0-byte body, because a truncated wheel fails pip's hash check far from
the cause.

## Connection Management

### Connection Lifecycle

1. **Accept**: `TcpListener::accept()` creates new TCP connection
2. **Register**: Connection added to `ServerInstance` with `ProtocolConnectionInfo::Pypi`
3. **Serve**: Hyper's `http1::Builder::new().serve_connection()` handles HTTP/1.1 protocol
4. **Request Loop**: Each request on the connection calls the service function
5. **LLM Call**: Service function calls LLM to generate response
6. **Close**: Connection removed when TCP socket closes (client disconnect or error)

### Connection Data Structure

```rust
ProtocolConnectionInfo::Pypi {
    recent_requests: Vec<String>, // Track recent URIs requested
}
```

### State Updates

- Connection state tracked in `ServerInstance.connections`
- Each request/response pair calls `update_connection_stats` once, from the thin
  wrapper around the request handler: `bytes_received` (the request head plus its
  body), `bytes_sent` (the response body hyper will write), and one packet in each
  direction. That wrapper exists because the counters were **never updated at all** —
  this section claimed they were while every peer drew as idle with `0 ↓ 0 ↑`
- `bytes_received` is an estimate: hyper hands the handler a parsed `Request`, so the
  original head is reconstructed from the parts that survive. An estimate is the right
  answer here; a frozen 0 reads as "this peer sent nothing" rather than "we did not
  measure"
- `last_activity` therefore advances on every request
- UI updates via `__UPDATE_UI__` message

## Known Limitations

### 1. Binary Distributions Need a Handler

- `body` is UTF-8 text, sent byte for byte; `body_base64` is decoded first.
  Exactly one of the two must be present - the encoding is never guessed
- A model cannot write wheel or sdist bytes: pip rejects a malformed archive.
  Real distributions come from a script or static handler (e.g. a Python handler
  that builds a wheel with `zipfile` and base64-encodes it)
- For a honeypot or a metadata-only demo, serve text through `body` and accept
  that pip fails at the install step rather than the download step

### 2. No Package Validation

- No verification that returned HTML conforms to PEP 503
- No validation of file hashes (sha256)
- No checking of package metadata format

### 3. No Authentication

- No support for authenticated package repositories
- No API tokens or user credentials
- Public repository only

### 4. No Package Upload

- PEP 503 only covers package download (Simple Repository API)
- Package upload (PEP 691, Warehouse API) not implemented
- Read-only repository

### 5. HTTP/1.1 Only

- No HTTP/2 support
- No TLS/HTTPS support (plain HTTP only)
- Should use localhost or private networks

### 6. No Caching

- No ETag or Last-Modified support
- No conditional requests
- Every request results in LLM call (slow)

### 7. Memory Constraints

- **Responses** are fully buffered in memory: a large wheel served through
  `body_base64` is held whole, and there is no streaming
- **Requests** are capped at `MAX_REQUEST_BODY_BYTES` (8 MiB) and refused with 413
  above it, so the inbound side is not a peer-controlled allocation

### 8. Request-Only

- `metadata()` declares `.request_only(…)`: "PyPI is HTTP request/response; a server cannot send a
  peer anything unprompted". The dashboard's `[ send message ]` on a peer is disabled and shows
  that reason, and MCP `send_to_peer` refuses with it.

## Example Prompts

### Simple Single Package

```
listen on port 8080 via pypi
Serve a package called "hello-world" version 1.0.0
When pip requests package list, return hello-world
When pip requests hello-world files, return a wheel file: hello_world-1.0.0-py3-none-any.whl
When pip downloads the wheel, return a minimal zip file with PKG-INFO
```

### Multiple Packages

```
listen on port 8080 via pypi
Serve three packages:
1. "requests" with version 2.28.0
2. "numpy" with versions 1.24.0 and 1.25.0
3. "pandas" with version 2.0.0
Return appropriate HTML for package list and file lists
Return placeholder wheel files when downloaded
```

### Conditional Package Availability

```
listen on port 8080 via pypi
Serve packages based on request headers:
- If User-Agent contains "pip", serve "example-pkg" version 1.0.0
- If User-Agent contains "poetry", serve version 1.1.0
- Otherwise return 404
```

### Dynamic Package Generation

```
listen on port 8080 via pypi
Act as a dynamic PyPI mirror:
- When pip requests any package, claim it exists
- Generate version 0.0.1 for any package
- Return minimal wheel files with just PKG-INFO metadata
```

## Performance Characteristics

### Latency

- One LLM call per HTTP request
- Typical latency: 2-5 seconds per request with qwen3-coder:30b
- pip makes multiple requests: index, package page, file download

### Throughput

- Limited by LLM response time (2-5s per request)
- pip install may take 10-15 seconds for single package (multiple requests)

### Concurrency

- Multiple pip clients can install concurrently
- Each request processed on separate tokio task
- Ollama lock serializes LLM API calls

### Memory Usage

- Each request/response buffered in memory
- Package files (wheels) can be large (10-100MB)
- Multiple concurrent requests may exhaust memory

## Use Cases

### 1. Internal Package Repository

Host internal/private Python packages:

```
listen on port 8080 via pypi
Serve our company's internal packages:
- "internal-auth" version 2.1.0
- "data-pipeline" version 1.5.3
- "ml-utils" version 3.2.0
```

### 2. PyPI Honeypot

Monitor pip install attempts:

```
listen on port 8080 via pypi
Act as a honeypot PyPI server
Log all package requests with IP addresses
Return fake packages to simulate a real repository
```

### 3. Testing & Development

Test pip behavior with unusual responses:

```
listen on port 8080 via pypi
Return random HTTP status codes for testing
Sometimes return valid packages, sometimes 404
Simulate slow responses (10+ seconds)
```

### 4. Educational/Demo

Demonstrate how PyPI works:

```
listen on port 8080 via pypi
Explain each pip request in plain English
Show what pip is asking for and why
Return minimal but valid responses
```

## Future Enhancements

### PEP 691 JSON API

Add JSON endpoint support:

- `/simple/` with `Accept: application/vnd.pypi.simple.v1+json`
- Return JSON instead of HTML
- More machine-readable than HTML

### Package Upload (Warehouse API)

Support package publishing:

- POST `/legacy/` endpoint (twine upload)
- Authentication with API tokens
- Package storage backend

### HTTPS Support

Add TLS for secure package downloads:

- Prevents MITM attacks
- Required for production PyPI mirrors

### Package Caching

Cache package metadata and files:

- Reduce LLM calls for repeated requests
- ETag and Last-Modified support
- Faster responses for pip

### Streaming Large Files

Support streaming package downloads:

- Don't buffer entire wheel in memory
- Allow >100MB packages
- Chunked transfer encoding

### Metadata Validation

Validate LLM-generated responses:

- Check PEP 503 HTML format
- Verify file hashes match
- Ensure proper URL structure

## Connection bounds

Before September 2026 this server accepted without limit and bounded no read in time, so a peer
that connected and said nothing held a socket, a connection task and an `AppState` entry forever,
pre-authentication, on a server that would happily accept a hundred more. It now declares both
halves; the constants and the reasoning live beside them in `src/server/pypi/mod.rs`.

| Bound | Value | Why this number |
|---|---|---|
| `FIRST_BYTE_READ_TIMEOUT` | 30s | HTTP is client-speaks-first, so a peer that has connected and sent no byte has begun no request. 30s sits between nginx's `client_header_timeout` default of 60s and Apache's `RequestReadTimeout header=20`. Enforced with `TcpStream::peek` before the socket reaches hyper, so the request line is still there for hyper afterwards. |
| `IDLE_BETWEEN_REQUESTS_TIMEOUT` | 300s | Twenty times pip's own socket timeout (`--timeout`, 15s by default), so a pip still waiting on us gave up long ago, and four times nginx's `keepalive_timeout` default of 75s. What is inside the window is pip resolving the next requirement or installing the wheel it just fetched. |
| `MAX_CONNECTIONS` | 256 | Each admitted connection may hold one whole in-memory response body (a simple-index page or a wheel), so the cap turns that per-connection bound into a total one. Refusal: **HTTP/1.1 `503 Service Unavailable` with `Retry-After: 5`** — pip treats a 503 as retryable and backs off. Nothing of netget's reaches the wire; the reason is logged under `decision=fail_closed_connection_cap`. |

**NetGet's own PyPI client is *lazy*, so it is never the silent peer this bound closes:**
`src/client/pypi/mod.rs` resolves an index URL and opens no socket until a fetch runs from an
action — `PROTOCOL_QUALITY.md`'s three-state test.

**The idle bound is a watchdog, not a read deadline, and that is not a stylistic choice.** hyper
owns every read once `serve_connection` starts and keeps polling the connection for new frames
*while a request is being answered*, so a deadline on those reads would fire in the middle of an
LLM round-trip. It watches `ConnectionActivity` instead, which reports a connection with work in
flight as not idle at all — so the model round-trip, and a `manual` rule parking an event for a
human (`src/state/intercepts.rs`, 300s by default), sit outside every deadline by construction.
That is the `.connectionless()` lesson in the project `AGENTS.md` read in reverse: TFTP evicted
live transfers because "idle" was measured wrongly.

**One residual, stated rather than hidden.** The first-byte bound is discharged the moment any
byte arrives, so a peer that sends one byte of a request line and then stops is bounded by the
*idle* deadline (300s) rather than by the 30s one. hyper's own `header_read_timeout` cannot
express the pair: it re-arms whenever hyper starts reading a head, an idle keep-alive connection
included, so setting it to 30s would close every pooled client between requests — collapsing the
two bounds onto one number, which is exactly what the pair exists to avoid.

`tests/server/pypi/connection_bounds_test.rs` drives all three from the wire, over
`tests/helpers/http_bounds.rs`. Each was verified by **removing** the bound and watching the test
fail: with the `peek` deadline gone the silent peer still held the socket at 60s; with the idle
bound collapsed to 30s an answered connection was closed after 38s of silence; with the permit
released early the connection past the cap was served instead of refused.
